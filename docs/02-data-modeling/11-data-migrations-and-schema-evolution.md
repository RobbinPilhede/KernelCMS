# Data Migrations & Schema Evolution

In KernelCMS your content schema lives in `kernel.config.ts` as config-as-code, but the database underneath it is still a physical artifact that has to change in lockstep. This document specifies how KernelCMS bridges the two: how migration files are generated from schema diffs, when to reach for handwritten migrations instead, how to run data backfills against millions of documents, and how to ship breaking schema changes without taking the API down. The throughline is that the config is the source of truth, the adapter owns the physical translation, and you always keep an escape hatch.

## The migration model

KernelCMS treats schema and data as two separate evolution problems that happen to travel together.

- **Schema evolution** is structural: a new column, a renamed table, a dropped index, a changed `not null` constraint. For SQL backends this is owned by Drizzle, the default ORM across `@kernel/db-postgres`, `@kernel/db-sqlite`, and `@kernel/db-mysql`. For document-oriented workloads, `@kernel/db-mongodb` has no DDL, so its "schema" migrations are really validator and index changes.
- **Data evolution** is semantic: existing documents need their field values transformed to satisfy the new schema (split a `name` into `firstName`/`lastName`, normalize a `select` value, populate a new required field). This is always handwritten — no diff engine can infer your business rules.

Every backend implements the same `Adapter` contract (see Adapters & the persistence layer), so the migration _workflow_ is identical regardless of database. What differs is the generated SQL/commands the adapter emits.

```
kernel.config.ts ──diff──▶ migration file ──apply──▶ database
   (intent)                 (generated + edited)        (state)
        ▲                                                   │
        └───────────────── reconcile (status) ◀─────────────┘
```

Payload bundles its own migration runner per database adapter; Strapi historically auto-altered tables on boot (convenient, terrifying in production); Sanity has no migrations at all because its datastore is schemaless and content "migrations" are scripts you run against the Content Lake. KernelCMS deliberately lands closer to Payload: explicit, versioned, reviewable migration files — but generated by Drizzle's diffing and runnable through the `kernel` CLI with the same query core (`where` / `sort` / `depth`) you already use everywhere else.

## Migration files

A migration is a directory under `migrations/` containing a timestamped file pair: the runnable migration and a frozen snapshot of the schema it produced. The snapshot is what the diff engine compares against next time, so generation never re-derives state from a live database.

```
migrations/
  0000_initial.ts
  0001_add_seo_group.ts
  0002_posts_status_backfill.ts
  meta/
    0000_snapshot.json
    0001_snapshot.json
    _journal.json
```

Each migration exports `up` and `down`. The runner is transactional where the engine allows it (Postgres wraps the whole migration in a transaction; SQLite and MySQL have weaker DDL transactionality, which the adapter surfaces as a warning).

```ts
import { defineMigration } from '@kernel/db'

export default defineMigration({
  name: '0001_add_seo_group',
  async up({ db, sql }) {
    await db.execute(sql`
      ALTER TABLE "posts"
      ADD COLUMN "seo_title" varchar(160),
      ADD COLUMN "seo_description" text
    `)
  },
  async down({ db, sql }) {
    await db.execute(sql`
      ALTER TABLE "posts"
      DROP COLUMN "seo_title",
      DROP COLUMN "seo_description"
    `)
  },
})
```

`_journal.json` records which migrations have run, in order, with a content hash. The runner refuses to apply a migration whose hash changed after it was committed to the journal — you edited an already-applied file, which is almost always a mistake. CLI surface:

| Command                         | Effect                                                                |
| ------------------------------- | --------------------------------------------------------------------- |
| `kernel migrate generate`       | Diff config against latest snapshot, write a new migration + snapshot |
| `kernel migrate up`             | Apply pending migrations in journal order                             |
| `kernel migrate down --to 0001` | Roll back to a target                                                 |
| `kernel migrate status`         | Show applied vs. pending and detect schema drift                      |
| `kernel migrate dev`            | Generate + apply in one step (dev only, never CI/prod)                |

`kernel migrate status` also runs a **drift check**: it diffs the live database against the latest snapshot and fails if someone hand-altered the database out of band. This is the guard rail Strapi's boot-time auto-migrate never had.

## Generated vs. handwritten

The default path is generation. You change `kernel.config.ts`, run `kernel migrate generate`, and Drizzle's differ emits the DDL. Generation is correct and complete for purely structural changes:

```ts
// kernel.config.ts
export const Posts = defineCollection({
  slug: 'posts',
  fields: [
    text('title', { required: true }),
    group('seo', {
      fields: [text('title', { maxLength: 160 }), textarea('description')],
    }),
    select('status', { options: ['draft', 'published'], defaultValue: 'draft' }),
  ],
})
```

Run `kernel migrate generate` and you get the `seo_*` columns and the `status` column with its check constraint, plus the parallel changes to the versions table (KernelCMS keeps version history with autosave — see [Drafts, publish & versions](./10-versioning-drafts-and-autosave.md), so every collection field change touches both `posts` and `_posts_versions`).

Generation cannot infer **intent** in three cases, and these are where you edit the generated file or write one by hand:

1. **Renames.** A diff sees a dropped `name` column and an added `fullName` column — it will `DROP`/`ADD` and silently destroy data. KernelCMS prompts on ambiguous diffs (`Did you rename "name" → "fullName"? [rename/separate]`) but you should verify the emitted `ALTER ... RENAME COLUMN` before committing.
2. **Data transforms.** Any change where new column values must be derived from old ones. The generator stubs the structural part and leaves a `// TODO: backfill` marker; you fill in the data step (next section).
3. **Custom physical layout.** Partial indexes, generated columns, `GIN` indexes on `json` fields, table partitioning. Drizzle won't emit these from field config, so you append raw `sql` to the generated `up`.

The rule we enforce in review: **generated migrations are a starting point, never the final answer for anything touching existing rows.** A generated migration that only adds nullable columns or new tables can ship as-is. Anything that drops, renames, narrows a type, or adds a `not null` constraint gets a human-authored data step attached.

For `@kernel/db-mongodb`, "generation" emits `$jsonSchema` validator updates and index `createIndex`/`dropIndex` operations rather than DDL, but the file shape and journal mechanics are identical.

## Data backfills

A backfill is a migration that mutates existing document data. KernelCMS gives you two execution levels, and choosing correctly is the whole game.

**Level 1 — raw SQL** for set-based transforms the database can do in bulk. Fastest, but bypasses hooks, validation, and access control.

```ts
async up({ db, sql }) {
  await db.execute(sql`UPDATE "posts" SET "status" = 'published' WHERE "_status" = 'live'`)
}
```

**Level 2 — Local API** for transforms that must run your business logic: field hooks, computed values, validation, relationship resolution, localization. This calls the same in-process operation core (`@kernel/core`) the REST/GraphQL/RPC surfaces use, with full type inference. Slower per document, correct by construction.

```ts
import { getPayload } from '@kernel/core'

async up({ config }) {
  const kernel = await getPayload({ config })

  // Batch through the typed Local API so hooks + validation run.
  for await (const batch of kernel.find.stream('authors', {
    where: { fullName: { exists: false } },
    limit: 500,
    depth: 0,
  })) {
    for (const author of batch.docs) {
      await kernel.update('authors', author.id, {
        data: { fullName: `${author.firstName} ${author.lastName}`.trim() },
        // Skip revalidation/webhooks during bulk backfill.
        context: { migration: true },
      })
    }
  }
}
```

Guidance on choosing:

| Concern                 | Raw SQL (Level 1)        | Local API (Level 2)     |
| ----------------------- | ------------------------ | ----------------------- |
| Throughput              | Millions/min             | Thousands/min           |
| Runs field hooks        | No                       | Yes                     |
| Validates output        | No                       | Yes                     |
| Localized fields        | Manual JSON surgery      | Handled                 |
| Version history written | No (intentional)         | Optional via `context`  |
| Use when                | Mechanical value mapping | Business logic required |

`kernel.find.stream` is backed by TanStack DB-style cursored reads on the server so a backfill never loads the whole collection into memory. Always paginate by an immutable cursor (the document `id` / `createdAt`), never `OFFSET` — offset pagination drifts when rows change under you.

Make backfills **idempotent and resumable**. Filter on the post-condition (`fullName: { exists: false }`), not a side channel, so re-running the migration after a crash only touches unfinished rows. For backfills too large to fit one deploy window, write them as a standalone job under `jobs/` driven by the queue adapter rather than a boot-time migration, and have the migration merely enqueue it. This is where Sanity users have to hand-roll everything against the Content Lake API; KernelCMS gives the streamed, typed, hook-aware path out of the box.

## Zero-downtime schema changes

The enemy is the window where new code expects a schema the old running instances don't have, or vice versa. KernelCMS standardizes on the **expand / migrate / contract** pattern, and the API layer is explicitly designed to tolerate the intermediate state.

```
phase 1 EXPAND     phase 2 MIGRATE      phase 3 CONTRACT
add new (nullable)  backfill + dual-write drop old column
column; deploy      then make required   after all reads
code that writes     and cut reads over   moved
both old + new
   │                      │                      │
   ▼                      ▼                      ▼
no downtime          no downtime           no downtime
```

A column rename `name → fullName` done safely:

1. **Expand.** Add `full_name` (nullable). Deploy app code that writes both fields and reads `full_name` with a fallback to `name`. The generated migration here is additive-only, so it is safe to apply while old instances run.
2. **Migrate.** Run the Level 1 or Level 2 backfill to populate `full_name` for historical rows. Idempotent, resumable, runs against live traffic.
3. **Contract.** Once every instance reads `full_name` and the backfill is verified complete, ship a migration that drops `name` and adds the `not null` constraint to `full_name`.

The hard rule: **never combine an additive and a destructive change in one migration, and never make a column `not null` in the same release that introduces it.** Splitting across releases is what makes the deploy reversible at every step.

KernelCMS supports this directly with versioned field config. You mark the legacy field deprecated so the admin and APIs keep serving it during the transition without it being authored:

```ts
text('name', {
  deprecated: true, // hidden in admin, still readable via API
  virtual: { from: 'fullName' }, // read-through alias during the cutover
})
```

Operational guarantees the runner provides:

- **`CONCURRENTLY` for indexes.** On Postgres the adapter emits `CREATE INDEX CONCURRENTLY` (and runs it outside the migration transaction) so adding an index never holds a write lock. MySQL uses online DDL; SQLite rebuilds, so large-table index adds there get a loud warning.
- **Lock-timeout fencing.** Each DDL statement runs under a configurable `lock_timeout`/`statement_timeout` so a migration that can't get its lock fails fast instead of stalling every connection behind it.
- **Forward-only in production.** `down` migrations exist and are exercised in CI and staging, but production recovery is roll-forward: the expand/contract discipline means you can always deploy a corrective forward migration rather than rolling a destructive `down` against live data.

Compared to the field: Strapi's lifecycle of altering tables on startup makes true zero-downtime deploys hard because schema and code change atomically at boot; Payload supports the same expand/contract discipline but leaves more of the dual-write wiring to you; Sanity sidesteps schema locks entirely but pushes all consistency work into application code. KernelCMS's wager is that explicit, generated, reversible migration files plus a query core that tolerates the intermediate state give you Sanity's safety without giving up a real schema.

## Open questions

- **Multi-tenant migration fan-out.** For KernelCMS Cloud's multi-tenant hosting, do per-tenant backfills run as one queued job per tenant, or batched with a tenant cursor? Schema DDL is shared; data backfills are not. Leaning toward per-tenant queue jobs for blast-radius isolation.
- **Squashing.** Long-lived projects accumulate hundreds of migrations. Do we ship a `kernel migrate squash` that collapses applied migrations into a fresh baseline snapshot, and how does that interact with the journal hash guard?
- **Cross-adapter portability.** A migration written as raw `sql` is not portable across `@kernel/db-postgres` and `@kernel/db-mysql`. Should `defineMigration` offer a dialect-tagged variant, or do we accept that handwritten data steps are adapter-specific by nature?
