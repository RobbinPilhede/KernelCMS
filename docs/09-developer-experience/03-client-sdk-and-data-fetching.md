# Client SDK & Data Fetching

`@kernel/client` is the typed client your frontend talks to. It wraps the same operation core that powers the Local API, the REST surface, and the GraphQL resolvers, and it ships first-class TanStack Query bindings so React frontends get caching, deduplication, and invalidation without writing a fetch layer. The types are generated from your `kernel.config.ts` — collections, fields, locales, and the shared query language — so a typo in a `where` clause or a missing `select` field is a compile error, not a runtime 400. This document specifies the client, its query and mutation helpers, the TanStack Query hooks, and how caching and invalidation work end to end.

## The typed client

You create one client per app. It holds the base URL, auth strategy, and the generated type map. Everything else hangs off it.

```ts
// lib/kernel.ts
import { createClient } from '@kernel/client'
import type { Kernel } from '@/kernel-types' // generated by `kernel generate`

export const kernel = createClient<Kernel>({
  url: process.env.NEXT_PUBLIC_KERNEL_URL!, // e.g. https://cms.acme.com
  // Auth is pluggable. Token for SSR/service calls; cookie session for the browser.
  auth: { mode: 'cookie' }, // or { mode: 'token', token: () => getToken() }
  defaults: { depth: 1, locale: 'en' },
})
```

The `Kernel` type is the contract. It's produced by `kernel generate` from your config and regenerated on every schema change. Each collection becomes a fully-typed accessor:

```ts
const post = await kernel.collections.posts.findByID({ id, depth: 2 })
//    ^? Post & { author: User; hero: Media }   ← depth-2 relationships resolved

const drafts = await kernel.collections.posts.find({
  where: { status: { equals: 'draft' }, publishedAt: { less_than: new Date() } },
  sort: '-publishedAt',
  limit: 20,
  select: { title: true, slug: true, author: { name: true } },
})
//    ^? PaginatedDocs<{ title: string; slug: string; author: { name: string } }>
```

Three things to notice. The `where` keys are the actual field names; the operators (`equals`, `less_than`, `in`, `contains`, `near`) are constrained to what each field type supports — you cannot write `near` on a `text` field. `select` narrows the return type, so the client never hands you fields you didn't ask for. And `depth` changes the shape of relationship fields from `string | id` to the resolved document type. This is the same query language documented in the query language reference; the client just makes it typed.

### How the client talks to the server

Under the hood the client speaks typed RPC over TanStack Start server functions — the same operations as the Local API, serialized over the wire. REST and GraphQL remain available for non-TypeScript consumers, but TS frontends should prefer RPC because it is the only transport that carries full type inference, including `select` narrowing and `depth` resolution.

```
 frontend (browser/SSR)
        │  kernel.collections.posts.find(args)
        ▼
 @kernel/client ──► typed RPC (TanStack Start server fn) ──► @kernel/rpc
        │                                                         │
        │                                                  operation core
        │                                                  (access, hooks, validation)
        ▼                                                         ▼
   typed result  ◄────────────  same code path as Local API ◄── adapter (Drizzle/Mongo)
```

Payload exposes a Local API that only runs in-process on the server. Sanity's client is typed only if you bolt on a codegen step, and its GROQ queries are validated at runtime. Strapi's REST/GraphQL responses are typed by hand or via community generators. KernelCMS generates the types from config and ships them with the client, so the same call has the same type whether it runs in a server function, an SSR loader, or the browser.

## Query and mutation helpers

The client exposes the full operation set per collection and per global, plus auth helpers. These are plain async functions — no React required — so they work in route loaders, server functions, scripts, and tests.

| Helper                                     | Surface    | Returns                 |
| ------------------------------------------ | ---------- | ----------------------- |
| `find(args)`                               | collection | `PaginatedDocs<T>`      |
| `findByID(args)`                           | collection | `T`                     |
| `count(args)`                              | collection | `{ totalDocs: number }` |
| `create(args)`                             | collection | `T`                     |
| `update(args)` / `updateByID`              | collection | `T`                     |
| `delete(args)` / `deleteByID`              | collection | `T`                     |
| `findGlobal(args)`                         | global     | `T`                     |
| `updateGlobal(args)`                       | global     | `T`                     |
| `auth.login` / `logout` / `me` / `refresh` | auth       | session info            |

Read helpers accept the shared query language; write helpers accept typed `data` plus `depth`, `locale`, `draft`, and `overrideAccess` (server-only). Access control, validation, and hooks run server-side on every call regardless of transport, so a mutation issued from the browser is gated identically to one issued from a server function.

```ts
// Draft-aware read in an SSR loader
const preview = await kernel.collections.pages.findByID({
  id,
  draft: true,
  locale: 'de',
})

// Typed mutation — `data` is checked against the Page field config
const updated = await kernel.collections.pages.update({
  id,
  data: { title: 'Neuer Titel', hero: mediaId },
})
```

For one-off or non-TS callers you can drop to REST or GraphQL; see REST & GraphQL. The typed client is the recommended path for any TypeScript frontend.

## TanStack Query hooks

`@kernel/client/react` generates a React hook namespace from the same config. Every helper has a hook; query keys are derived from the operation and arguments, so you never hand-author a key. This is the integration layer Payload and Strapi leave to you — you'd normally write your own `useQuery` wrappers and key factories. KernelCMS ships them, typed.

```tsx
import { kernelQuery } from '@/lib/kernel' // createReactClient(kernel)

function PostList() {
  const { data, isLoading, error } = kernelQuery.posts.useFind({
    where: { status: { equals: 'published' } },
    sort: '-publishedAt',
    limit: 20,
  })

  if (isLoading) return <Spinner />
  if (error) return <ErrorState error={error} />
  if (!data?.docs.length) return <Empty />

  return (
    <ul>
      {data.docs.map((p) => (
        <PostRow key={p.id} post={p} />
      ))}
    </ul>
  )
}
```

The hooks honor the React rules in this project: loading, error, and empty states are first-class, and the data is fully typed including `select` narrowing. Query options pass through to TanStack Query, so `staleTime`, `enabled`, `placeholderData`, and `select` (Query's, for client transforms) all work.

```tsx
// Infinite list backed by KernelCMS pagination
const q = kernelQuery.posts.useInfiniteFind(
  { limit: 25, sort: '-publishedAt' },
  { getNextPageParam: (last) => last.nextPage ?? undefined },
)
```

Pair `useInfiniteFind` with TanStack Virtual for long collections — the admin uses the same combination for its list views, so the frontend story matches. See the admin overview.

### Mutation hooks

```tsx
const { mutate, isPending } = kernelQuery.pages.useUpdate({
  onSuccess: (doc) => toast.success(`Saved ${doc.title}`),
})

mutate({ id, data: { title } })
```

Mutation hooks return typed inputs and outputs and integrate with the invalidation rules below.

## Caching and invalidation

The client maps every operation to a deterministic query key so caching, deduplication, and invalidation are automatic and predictable.

```
['kernel', collectionSlug, operation, normalizedArgs]
// examples
['kernel', 'posts', 'find',     { where, sort, limit, page, depth, locale }]
['kernel', 'posts', 'findByID', { id, depth, locale, draft }]
['kernel', 'globals', 'find',   { slug: 'settings', locale }]
```

Arguments are normalized (stable key ordering, default-filled) before hashing, so two semantically identical queries share a cache entry. After a mutation, the client invalidates by precise rules rather than nuking the cache:

| Mutation                | Invalidates                                                               |
| ----------------------- | ------------------------------------------------------------------------- |
| `create`                | all `find`/`count` lists for that collection                              |
| `update` / `updateByID` | that doc's `findByID` key + all `find`/`count` lists for the collection   |
| `delete`                | that doc's `findByID` key + lists; removes the doc from cached list pages |
| `updateGlobal`          | that global's key                                                         |

Mutation hooks can also write the server response straight into the `findByID` cache to skip a refetch, and you can opt into optimistic updates with rollback:

```tsx
kernelQuery.pages.useUpdate({
  optimistic: (prev, vars) => ({ ...prev, ...vars.data }), // applied immediately, rolled back on error
})
```

Relationship invalidation deserves attention. When a referenced document changes, lists that resolved it at `depth > 0` are stale. The client tracks resolved relationship IDs per cached entry and invalidates dependents on the related collection's mutations — so editing an author refreshes the post lists that embedded that author, without a blanket invalidation.

### SSR hydration

For TanStack Start and Next.js, prefetch on the server and hydrate the client cache so the first paint has data and no waterfall:

```ts
await queryClient.prefetchQuery(kernelQuery.posts.findOptions({ limit: 20 }))
// dehydrate(queryClient) → pass to the client boundary
```

### Live and offline (TanStack DB)

For live or offline frontends, opt into reactive client-side collections backed by TanStack DB. The client syncs a collection into a local store and pushes server changes through subscriptions, so components read from a reactive source instead of polling. This is the same primitive the admin uses for live preview; see [live preview](../04-admin-ui/10-live-preview-and-visual-editing.md). Sanity's live content and Strapi's manual polling are the points of comparison — KernelCMS keeps it in the typed client.

## Open questions

- **Realtime transport:** SSE versus WebSocket for the TanStack DB sync channel, and whether the choice is a `@kernel/client` adapter or fixed per deployment runtime (edge vs. Node).
- **Cross-tab cache sharing:** whether to share the Query cache across browser tabs via `BroadcastChannel` by default, or leave it opt-in.
- **Relationship-dependency tracking cost:** the per-entry resolved-ID index makes invalidation precise but grows with cache size; we may cap tracking depth or fall back to collection-level invalidation past a threshold.
- **Persisted-query mode:** whether to support hashing `find` queries into named persisted queries for CDN-cacheable reads on KernelCMS Cloud.
